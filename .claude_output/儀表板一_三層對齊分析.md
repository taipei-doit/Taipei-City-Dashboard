## TL;DR

評估報告 4 個 component 的 spec，**經過 DE 規劃文件「修正」後改了 1 個（C3）**，後來 FE 實作時又**自行改了 1 個（C4）**。最終 4 個 component 沒有任何一層完全對齊：

| 卡片 | 評估報告 → DE 規劃 → 實作 | 偏離方 |
|---|---|---|
| C1 | ✅ → ✅ → ✅ | 無 |
| C2 | ✅ → ⚠️（簡化） → ⚠️（沿用簡化） | DE 規劃 + FE 都簡化了 join |
| **C3** | 異常類型圓餅 → **改成 30 天趨勢** → 又改回類型分布 | **DE 規劃偏了**，FE 反而對齊評估報告 |
| **C4** | 站點底圖 marker → 站點底圖 marker → **改成 legend cards** | **FE 偏了**，DE 規劃對齊評估報告 |

## 3. 偏離的根因

### 3.1 DE 規劃為什麼偏 C3

DE 規劃 §11 修正紀錄：

> §8 C3：原規劃 `equipment_type` 分布 → 改為「過去 30 天各線公告數」（**equipment_type 不存在**）

問題：
- 「`00001517` 沒 equipment_type 欄位」這個觀察是對的
- 但結論「改為 30 天趨勢」是錯的：**評估報告 C2 已經明示「`00001517 + 00001516` join by station」**，同樣的 join 思路可以延伸到 C3 — 用 `00001516` (elevator) 表的 `facility_type` 欄位 JOIN 還原
- DE 規劃在「修正」時，**沒回頭對照評估報告判斷主題是否被改變**

這是 `plan-de-dag-from-eval` skill 的盲點：發現欄位缺失就獨立決定替代主題，沒看相鄰 component 的 join 範例。

### 3.2 FE PR #5 為什麼偏 C4

FE 改成 `[{name:"異常",value:N},{name:"正常",value:M}]` 這種兩列 legend cards 而不是地圖 marker 著色。

從評估報告 C4 描述「撈所有站，前端 marker 上色」明確是地圖視角，但 FE 把它改成了統計卡片視角。沒看到 PR description 寫為什麼改，**推測是 ray 沒對照評估報告，自行詮釋**。

### 3.3 BE PR #3 對齊 DE 規劃，但 DE 規劃偏了 C3

BE PR #3 chester 寫的是 `/alert-trend-30d`，這對齊 DE 規劃 §8。問題是 DE 規劃本身偏離了評估報告，BE 順著 DE 規劃做就一起偏了。

## 4. 修正方案

### 4.1 implementation 層

**C3：保留我補的 `/alert-by-type`** ✅
- 對齊評估報告原意「電梯／坡道／其他」分布
- BE 用 `mrtp_a11y_alert JOIN mrtp_a11y_elevator ON station` 取 facility_type
- `/alert-trend-30d` 可拔掉（DE 規劃私自加的，無 component 對應）或當 history 加值保留

**C4：拔掉我補的 `/station-overview`，FE 改打 `/stations`**
- `/stations` 已在 BE PR #3 實作，188 列 elevator + LEFT JOIN 取最新 active alert
- FE 改 transform：把 188 列攤成 GeoJSON FeatureCollection，套到 map layer，點位顏色看 `alert_status`
- 評估報告原意是地圖視角，[`MrtAccessibilityV2View.vue`](Taipei-City-Dashboard-FE/src/views/MrtAccessibilityV2View.vue) 中已有 `STATION_LAYER` 設定（顏色 match alert/normal），改完即可上色
- `mrt_station_demo.geojson` 寫死的 demo 資料可移除

**C2：可選擇要不要回 join**
- 評估報告 C2 寫「`00001517 + 00001516` join by station」
- 目前實作只用 alert 表的 `line` 欄，效果一樣（alert 表本來就有 line）
- 評估報告寫 join 的原因可能是想用 elevator 表當「全站集合」做分母（例：板南線異常 / 全部站數）
- 若要嚴格對齊評估報告，BE 要重寫 alert-by-line 加 elevator JOIN；不嚴格對齊則保留現況

### 4.2 skill 層

**`plan-de-dag-from-eval` skill 應加的檢查**：
1. 在發現欄位缺失（如 equipment_type 不存在）做修正建議時，**強制檢查同題目其他 dataset**有沒有可 join 的欄位 — 評估報告 C2 已示範，C3 不該獨立放棄
2. §11 修正紀錄產出時要明確標示「此修正是否改變 component 主題」；主題改變要二次確認回頭對照評估報告
3. 產出 DE 規劃前，最後一步把 §8 的 SQL 逐條跟評估報告 component table 對照，標示是否完全對齊

**`integration-audit` skill 應加的檢查**：
1. 追溯 spec ground truth 時，要爬到最上游的**評估報告**，不是 DE 規劃
2. 找到實作偏離 DE 規劃時，要先反問「DE 規劃是否本來就偏離評估報告」
3. 報告中三層比對改成顯式三欄（評估報告 → DE 規劃 → 實作），不是兩欄（規劃 → 實作）

### 4.3 流程層

未來開發新儀表板時的順序建議：
1. 評估報告為 spec ground truth，所有 PR description 應引用 evaluation report 的 line number
2. DE 規劃文件產出時，§11 修正紀錄如果改了 component 主題，必須在當下回 review 評估報告
3. FE 與 BE 開工前先把 component contract（path + request shape + response shape）寫到評估報告或專屬 contract 文件，雙方各自 review 對方的詮釋

```js
const c4Component = ref({

  chart_config: { types: ["MapLegend"], color: ["#ed5a5a", "#5fcf80"], ... },

```

`fetchAll()` 第 4 段 transform 改成：

```js
// C4 改打 /stations，回 188 列攤成 GeoJSON FeatureCollection 套地圖
const r4 = await axios.get("/api/v1/mrt/a11y/stations");
const features = (r4.data.data || []).map(s => ({
  type: "Feature",
  geometry: { type: "Point", coordinates: [s.lng, s.lat] },
  properties: {
    station_name: s.station,
    facility_name: s.facility_name,
    facility_type: s.facility_type,
    status: s.alert_status,  // 'active' / 'normal'
    alert_description: s.alert_description,
  },
}));
// 注入 mapStore 既有 layer 機制（取代寫死的 mrt_station_demo.geojson）
mapStore.setLayerGeoJson("mrt_station_demo", { type: "FeatureCollection", features });
```

對應地圖 layer paint 已是：
```js
"circle-color": [
  "match",
  ["get", "status"],
  "alert", "#ed5a5a",
  "normal", "#5fcf80",
  "#888888",
],
```

→ 完全相容，差別只在資料來源從寫死 GeoJSON 改成 BE 撈。

C4 的「儀表板總覽」面板可保留小卡片（如「目前 N 站異常」），但這跟 C1 重複，建議移除 C4 的卡片視角，C4 純走 mapview。
