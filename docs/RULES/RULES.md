2026 雙北程式設計節：城市儀表板大黑客松 — 技術開發與資安合規準則 (rules.md)

1. 競賽願景與核心轉型定位：從視覺化到自動化決策

1.1 戰略背景引言

隨著 2026 年雙北治理進入「AI 數據驅動」元年，城市儀表板的定位已發生根本性轉變。本顧問要求所有參賽團隊必須超越單純的「數據展示」，致力於構建一個AI 驅動的治理決策中樞。透過整合台北（Taipei）與新北（Metro-Taipei）的跨域資料，系統須具備在極端複合災難下，協助指揮官於 30 秒內完成風險評估與決策下達的能力。

1.2 核心轉型目標：價值層級演進

參賽作品必須對準「2026 AI 驅動期」的技術要求，實現從資訊呈現到自動化決策的跨越。

演進階段	核心關鍵	功能層級	價值層級演進 (Architect's Requirement)
2021-24 奠基期	資料開放	數據「可看、可用」	資訊呈現 (Information Presentation)
2025 多城市期	跨域平台	數據「分析與比較」	洞察產出 (Insight Generation)
2026 AI 驅動期	決策中樞	數據「輔助決策」	行動決策 (Action/Decision Support)

技術架構師指令： 2026 年的終極目標是「自動化洞察與決策輔助 (Semi-automated Decision)」。系統不再僅是顯示圖表，而是必須具備產出具體治理建議與執行方案的能力。

2. 競賽基本規則與開源合規要求

2.1 法律與 AGPL 授權義務

本競賽產出之原始碼受 AGPL 授權條款 約束。領獎前提為必須在賽後 2 個月內 完成技術整併。

2.2 四大類別 PR 整併計畫 (Mandatory PR Batches)

得獎團隊須依據本顧問制定之標準，將成果分批提交 Pull Request (PR) 回官方 Repo，否則視同未完賽：

1. Schema PR：定義劇本 JSON Schema 與 TypeScript Types（確保資料格式標準化）。
2. Dashboard Widgets PR：地圖圖層、動態時間軸、KPI 卡片與決策摘要元件。
3. Adapters PR：包含 MiroFishAdapter 或 MATSimAdapter 等異質系統介接模組。
4. Sample Scenarios PR：提交 5 個預製劇本與模擬結果數據。

2.3 演示限制 (Strict No-PPT Policy)

嚴格禁止使用簡報軟體。所有開發成果必須透過實機展示，違反者將取消評分資格。

階段	展示時間	演示要求與四大核心要素
初選	2 分鐘	受眾 (Audience)：如應變指揮官。<br>場景 (Scenario)：複合災難情境。<br>資料來源 (Data Sources)：跨縣市開放資料。<br>技術細節 (Technical Details)：LLM 整合與資料流邏輯。
決選	5 分鐘	實機操作：展示 AI 決策卡片與「副作用視覺化」互動。

3. 技術棧與儀表板 v3.0 資料庫架構

3.1 核心技術清單

分類	指定技術 (Non-negotiable)
前端 (Frontend)	Vue, Mapbox (GL JS), Apexcharts, Tailwind CSS
後端 (Backend)	Go, Gin, Gorm, PostgreSQL (PostGIS), Redis
資料處理	Python (Pandas/Scikit-learn), Cobra CLI

3.2 儀表板 v3.0：四表配置架構指令

為支援「台北」與「雙北」無縫切換，資料庫必須嚴格執行以下配置：

1. Component：儲存組件核心名稱與 Metadata。
2. Query Chart (關鍵表)：
  * CT (City) 欄位：必填。台北設為 Taipei；雙北設為 Metro-Taipei。
  * 避坑指南：建置雙北組件時，系統強制要求必須預先存在一筆台北的設定。
  * MapConfig IDs 欄位：本欄位為強制項，用於串聯 Component Maps 以載入不同城市的預設視野。
3. Component Chart：
  * 文字單位圖 (Text Unit Chart) 強制規範：Query Type 必須設為 3D。SQL 查詢中的 icon 欄位必須對接單位，如 %、persons 或 TWD。
4. Component Maps：管理不同城市之圖層編號與中心點視野。

4. AI 驅動架構與「副作用視覺化」規範

4.1 AI 系統流程建模

標準資料流：User Request \rightarrow LLM Analysis (Intent Mapping) \rightarrow Tool Router (Action) \rightarrow Final Response.

4.2 技術核心：Tool Calling 與行為邊界

* Intent Mapping：LLM 必須根據對話解析出包含參數的 tool_calls 格式。
* 副作用視覺化 (Core AI Requirement)：此為區分作品優劣之關鍵指標。 當使用者滑鼠懸停 (Hover) 於 AI 生成之「決策卡片」時，地圖必須即時高亮受影響路段或區域（如：下令關閉水門，地圖須顯示預期壅塞路段）。

4.3 AI 行為邊界 (The Boundary)

* 核准行為：跨城市數據摘要、情境對比、決策話術草稿、風險副作用分析。
* 禁止行為：黑箱預測 (Lack of data source)、全 Vibe Coding (無法維護之生成代碼)、使用非大會指定之外部模型。

5. 資安治理與環境配置規範 (Security First)

5.1 密鑰管理 (API_KEY_MGMT)

嚴禁將 API Key 硬編碼於原始碼中。所有密鑰必須透過環境變數 (ENV) 管理，且必須使用以下標準命名：

環境變數名稱	規範說明
TWCC_API_URL	https://api-ams.twcc.ai/api
TWCC_API_KEY	透過大會核發之 API Key
TWCC_MODEL	指定之 LLM Model Profile

5.2 傳輸與隔離

* 傳輸規則：Timeout: 60s, Max Retry: 2。
* 架構設計：必須透過代理伺服器 (Proxy Server) 封裝 API 請求，禁止前端直接暴露密鑰。

6. 兩日開發排程與 70-20-10 策略

6.1 任務部署

* 第一日 (底盤期)：環境配置 (Fork Repo)、資料清理流程建立、導入預製情境劇本。
* 第二日 (AI 整合期)：對接 TWCC API、完善 Tool Calling 邏輯、優化決策卡片 UX（含副作用視覺化）、整合「決策節點倒數」機制。

6.2 70-20-10 戰術分配

* 70% 準備底盤：賽前建置完成地圖/圖表模組與通用的 API 骨架。
* 20% 準備場景殼：設計「風險監測型」與「資源分配型」等通用模板。
* 10% 當天選題機制：題目公布後 30-60 分鐘內必須定案。組長須快速評估資料可得性，並根據「強制撤離令觸發」等邏輯進行選題。
