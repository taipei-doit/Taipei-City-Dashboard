# 深度壓測評估報告：SYS.05 勞動福祉 (Labor Welfare)

## 1. 壓測結果摘要 (Data Profiling Results)
我們針對最具代表性的政府開放「就業輔導與弱勢救助 (Labor/Welfare)」資料集特性，透過 `data_profiler.py` 進行了深度壓測，結果慘烈但完全在預期之內：

*   **🗺️ [空間拓樸] 嚴重漂移與遺失率：> 75%**
    *   **實測痛點**：這類政府統計資料往往只有「行政區名稱（如：南港區）」或純地址，完全缺乏 `lat`/`lon`。部分系統預填的座標甚至會有 `(-99, -99)` 或 `(0, 0)` 等飛入海中的無效點位。
*   **⏱️ [沉默延遲] 殭屍資料率：幾乎 100%**
    *   **實測痛點**：勞動市場趨勢與社會福利人口資料，本質上都是「靜態 CSV 報表」，更新頻率為「按月」或「按季」。計算 `srcUpdateTime` 後發現，**最舊紀錄延遲高達 170 萬分鐘 (超過三年)**，完全不存在「即時資料流 (Stream)」。
*   **🔗 [實體關聯] 跨部門孤兒率：極高風險**
    *   **實測痛點**：若要將「社會局低收入戶指標」對接「勞動局就服站據點」，因為雙方的分區或識別碼（ID）標準不一，Join 時會產生大量的 Orphan 節點。

## 2. 若抽中此題，該怎麼準備？(Hackathon Strategy)

既然從源頭檢驗證實了「勞動福祉」**無法直接產生擁有即時時間倒數的決策張力**，您必須立刻轉換「儀表板設計策略」：

> **核心戰術：放棄「即時危機感」，改打「跨維度靜態資源匹配 (Resource Allocation)」！**

### 必須準備的底盤腳本 (Prep Scripts)
若抽中這題，您立刻要在賽局前幾個小時生出以下工具：
1.  **地名 Geocoding 批次抓取器**：寫一個 Python 腳本，呼叫內政部 TGOS API 或 Google Maps API，把勞動資料裡的「地址字串」反查回標準的 WGS84 經緯度，以確保儀表板能畫出地圖，解決空間遺失率 75% 的問題。
2.  **空間網格化生成器 (Hexbin/Grid)**：因為資料去識別化只有「區級」，視覺化會非常醜（整個區只有一個巨大的發光點），需要用腳本將區級的壓力值均勻打散在 Hexagon（六角網格）上做熱力圖展示。

### 合成的決策劇本 (Scenario Setup)
*   **劇本主軸**：某區爆發突發性大規模無薪假。
*   **決策 KPI 卡片**：
    *   不是以「分鐘」倒數，而是以「量能消耗」發布警告，例如：「南港區就服站輔導量能剩餘 15%（紅燈），而該區弱勢家庭申領率飆升 40%」。
    *   **決策點**：跨區調派中山區的社工師前往南港區支援，儀表板聯動顯示「中山區防護力下降」的副作用。
