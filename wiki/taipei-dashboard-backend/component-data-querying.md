# Component Data Querying

> Sources: Taipei Urban Intelligence Center, 2026-04-24
> Raw: [component data apis](../../raw/taipei-dashboard-backend/component data apis.md); [component config apis](../../raw/taipei-dashboard-backend/component config apis.md); [components db](../../raw/taipei-dashboard-backend/components db.md); [vector db apis](../../raw/taipei-dashboard-backend/vector db apis.md)

## Overview

Component chart and history data is queried from the `dashboard` database using SQL strings stored in `dashboardmanager` component configuration tables. The backend executes those queries and parses results into front-end data shapes according to each component's `query_type`.

## Query String Mechanism

`query_chart` and `query_history` are SQL strings stored in component configuration. They can include `%s` placeholders for time range values generated by the front end.

Chart data queries can have either zero placeholders or two placeholders. Zero-placeholder queries return as written. Two-placeholder queries receive start and end times.

History data defaults to `time` query type and must have three placeholders: timestep unit, start time, and end time. The timestep unit is calculated from the requested range, such as day, week, or month.

## Query Types

`two_d` expects rows with `x_axis` and numeric `data`, parsed into one series with `{ x, y }` points.

`three_d` expects `x_axis`, `y_axis`, numeric `data`, and optional `icon`, parsed into categories plus named series. For this and related query types, the SQL result must be ordered so x-axis and y-axis values parse correctly.

`percent` shares the `three_d` shape but carries front-end percentage restrictions.

`time` expects timestamp `x_axis`, string `y_axis`, and numeric `data`, parsed into named time-series arrays.

`map_legend` expects legend rows with `name`, `type`, optional `icon`, and numeric `value`.

## SQL Ordering and Zero Values

The docs specifically warn that `three_d`, `percent`, and `time` queries must order `x_axis` and `y_axis` so parsing is stable. They also recommend preserving zero-valued subcategories rather than omitting them, for example by generating all x-axis/y-axis combinations and left joining measured data.

## Data APIs

`GET /component/:id/chart` is guest-accessible. Optional `timefrom` and `timeto` query parameters constrain chart data when the component query supports time placeholders.

`GET /component/:id/history` is guest-accessible. `timefrom` and `timeto` are required for history data.

Both endpoints return parsed `data`; `three_d` and `percent` responses also include `categories`.

## Vector Search

`POST /api/v1/vector/component` is guest-accessible and accepts a query string. The backend converts the query to a vector and returns similar components with `id`, `index`, `name`, `city`, and similarity `score`.
