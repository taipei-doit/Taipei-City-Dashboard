## Overview

The data end stores prepared dashboard data in PostgreSQL tables under `db:dashboard/dashboard`. Standard tables combine dataset-specific columns with shared time, geometry, timestamp, and primary-key fields so backend queries and map-serving workflows can consume them consistently.

## Standard Table Shape

A standard data-end table contains dataset-specific columns plus common fields:

- `data_time`: recommended field for the time represented by the data content.
- `wkb_geometry`: optional spatial field using `EPSG:4326` and WKBGeometry.
- `_ctime`: row creation time.
- `_mtime`: row modification time.
- `ogc_fid`: numeric primary key when the dataset has no natural primary key.

`data_time` is distinct from retrieval or update time. A dataset may be fetched today, updated by its source yesterday, and describe last month. If the source has no content time, the docs recommend using source update time as a substitute.

`_ctime` and `_mtime` are usually identical unless a row has been updated. They can be generated by the project table-creation utility.

## Dataset Info

`db:dashboard/dashboard/dataset_info` stores metadata needed by downstream presentation. The common pipeline updates this table from each DAG's `data_infos` section, while the ETL can update `lasttime_in_data` based on the maximum content time in the prepared data.

This table is the data-end bridge for human-readable dataset name, update cadence, source information, geometry type, output coordinate system, dataset description, ETL description, sensitivity, and latest data-content time.

## Load Behaviors

Data-end load behavior is configured per DAG and reused by load utilities:

- `append` writes incoming rows without clearing existing rows.
- `replace` truncates the destination table before writing incoming rows.
- `current+history` writes the latest state to a current/default table and appends the same run to a history table.

The history-table naming convention is to append `_history` to the current table name. `current+history` is used when low-latency dashboard reads and long-term analytical retention are both needed.

## Table Creation

The documentation recommends generating SQL with `/dags/utils/generate_sql_to_create_DB_table.py` rather than letting ETL code mutate schema directly. This reflects a security and governance preference: database changes should be reviewed and run by database administrators instead of being performed automatically by data engineers.

`generate_sql_to_create_db_table` accepts a target table name and column map, then emits SQL that creates the dataset columns plus standard fields such as `ogc_fid`, `_ctime`, and `_mtime` with appropriate permissions. The companion delete-SQL generator removes a table, its sequence, and the `_mtime` trigger while tolerating missing objects.

## Metadata Before Development

The documentation recommends planning metadata before writing ETL code. Important fields include the source platform, owning agency or platform, source documentation URL, source data URL, transfer format, source range, source update frequency, sensitivity, maintenance method, Airflow schedule, database table name, primary key, and indexes.

For source range, use `snapshot`, `new event`, `slice window`, or `full history`. For table naming, prefer a source or agency prefix plus a data name in snake case, rather than an application-topic category.
